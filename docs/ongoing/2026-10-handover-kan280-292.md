### KAN-292: how it works

- Configure Business usually creates the business BEFORE Finance Settings is
  opened, so "business is new" cannot mean "first save". A new flag
  `Business.documentNumberingInitialized` records it.
- `utils/documentNumberingInitial.js` (pure): `isDocumentNumberingInitialized`
  is true when the flag is set OR any of the four counters is not 1. That means
  existing businesses need no migration, and a business with live counters can
  never be set again.
- `PUT /api/business/profile` takes the numbers only when the request carries
  `initializeDocumentNumbering=true` and the business is not initialized. The
  write is `findOneAndUpdate` with a filter that requires the flag unset and
  every counter still 1 or missing; if a document was issued in between, the
  profile saves WITHOUT the numbers (`updateExistingBusiness` in
  `businessProfileUpdate.js`).
- The profile response carries `documentNumberingInitialized`. The frontend
  treats a missing value as "already set" on purpose, so an older backend never
  shows editable fields it would ignore.
- Tests: `business.route.test.js` (8 new), `documentNumberingInitial.test.js`,
  `financial-settings-form/panel/numbering-helpers` tests, and a Playwright test
  in `Frontend/e2e/business-configuration.spec.ts` that stubs the profile and
  was NEVER RUN (needs the local stack and a support-admin sign-in).
- Verified locally with a real session: first save of 1005 / 105 / 510 / 125,
  the first automated invoice was INV-1005, next number 1006.

## Things learned this session

- **How a board gets linked to a workspace.** `persistBoardsInBackground`
  (`routes/workspace.js`) stores boards with `$setOnInsert` and no
  `workspaceId`. `POST /api/board` also ignores it. Only `PUT /api/board`
  (Board Configuration Save, support admin or owner) writes `workspaceId`, the
  label and `syncData` together. A board nobody configured has `workspaceId:
  null`: the scheduled run says "No boards to bill for workspace" and a manual
  sync says "Board exists in workspace null".
- **A scheduled run only bills items whose shift falls in the schedule's
  period.** A daily schedule covers the previous Sydney day; a monthly one the
  previous calendar month. NDIS Certification matches either `Scheduled Shift
  Start Date & Time` or `Actual Shift Start Date and Time`, with status
  Completed or Cancelled, Timesheet Approval Approved, and not already invoiced.
- **Locally, ISO+ cannot reach the app, so webhooks never arrive.** After
  changing an item in ISO+ use Resync Data on the board; the local copy is
  otherwise stale.
- **The scheduler is external.** Locally nothing ticks. `POST
  /api/scheduler/tick` with the per-kind key (`SCHEDULER_API_KEY_INVOICE` or
  `_STATEMENT` in `Backend/.env`) runs one kind. `AUTOMATION_ENABLED` must be
  true or the tick holds jobs back. To make a job due, set its `nextRunAt` in
  the `scheduledjobs` collection to the past.
